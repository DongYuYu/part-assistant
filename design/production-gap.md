# 和正式上線的差距

一句話：**核心流程和安全規則已經是產品會用的做法（冪等、人工確認、排名前的權限過濾、稽核、CI 擋分數、降級）；資料、身分、規模和實際使用的驗證，還是用公開資料和假資料做的原型。**

這份文件列出真的要上線還缺什麼，以及先做哪個。各元件已知的限制，詳見各設計文件的「限制」段落。

## 二、上線前一定要補的

| 面向 | 現在 | 正式系統需要 |
|---|---|---|
| **資料能不能出公司** | 檢索到的文件段落會送到 Claude API（雲端） | 先經法務和資安同意：企業合約、資料不保留、限定區域；或機密文件只用地端模型回答 |
| **身分** | 自己報身分（`--user`、`PART_ASSISTANT_USER`），誰都能說自己是 bob | SSO，從目錄服務取得角色和群組；MCP 改成 HTTP 加 OAuth，由 server 驗證 token |
| **權限模型** | 一條直線的三個等級 | 依部門、廠區、專案授權（RBAC / ABAC）；核准人不能是開單的人（職責分離） |
| **資料來源** | 9 份公開 datasheet、3 份虛構文件、SQLite 假資料 | 接上真正的料號、庫存、文件系統，並且定期同步；文件要經過上傳和審核流程才能進索引 |
| **工單** | 寫進本機的 SQLite | 寫進既有的工單系統，並且通知負責的人 |

## 三、品質證據

- 黃金樣本 50 題是開發者自己寫的，全部是公開 datasheet 的問題。48/48 只證明「想得到的問題」答得對。
- 真實使用者的問法會不同：中英混雜、打錯字、口語、一次問好幾件事、問到圖面或掃描檔。
- 正式系統需要：
  - 從試用者收集真實問題，擴充黃金樣本（建議 100 題以上），並且加入權限和版本的題目。
  - 每個回答提供讚和倒讚的回饋；倒讚的題目定期檢討，加進黃金樣本。
  - 定期抽樣，由人工評分，確認自動評分沒有偏掉。
  - 換模型或改 prompt 之前，都要先過同一組評測。

## 四、規模和維運

| 面向 | 現在 | 正式系統需要 |
|---|---|---|
| 同時使用 | 單人、本機；MCP 只支援 stdio | 多人共用的 HTTP 服務；Postgres 加向量資料庫 |
| 新增文件 | 手動執行 `chunk`（解析和向量有快取，只會算新的段落）；server 要重開才看得到 | 上傳、審核通過後自動進索引，不用重開 |
| 搜尋方式 | 每次把問題和全部 711 段的向量逐一比對（numpy） | 段落到幾十萬段以上時，改用向量資料庫的近似搜尋（ANN） |
| 文件格式 | 文字型 PDF、Markdown | 掃描檔（OCR）、中文文件、圖面、試算表 |
| 監控 | 有 trace（耗時、token、成本）；推論閘道有每人的速率限制、token 配額、用量表，以及 Prometheus 指標和 Grafana 面板（[gateway.md](gateway.md)）；沒有告警 | 告警；閘道跑多個副本（速率計數器已經可以放 Redis，金鑰和用量要從 SQLite 改到 Postgres） |
| 資料保護 | 向量快取沒加密，裡面有所有文件；稽核用 trigger 保護，但能直接改資料庫檔案的人還是能刪 | 依權限分開存放或加密；稽核紀錄送到只能新增的外部儲存，並訂保存期限 |
| 介面 | CLI、MCP host | 網頁，或接到使用者已經在用的通訊工具 |

## 五、先做哪個

1. **資料能不能出公司**：答案決定架構。不能出去，就要先做地端推論（第二階段的 vLLM），雲端模型只處理公開資料。
2. **SSO 身分**：沒有可信的身分，權限過濾和稽核紀錄都只是形式。
3. **用真實問題擴充評測**：先找一條產線小範圍試用，收集問題和回饋，達到門檻再擴大。

順序的理由：前兩項不做就**不能**上線；第三項決定上線後**好不好用**。規模和維運可以隨使用人數再補。
