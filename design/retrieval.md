# 檢索（retrieval）設計

> 程式：[`src/part_assistant/retrieve.py`](../src/part_assistant/retrieve.py)、[`eval_retrieval.py`](../src/part_assistant/eval_retrieval.py)
> 測試：[`tests/test_retrieve.py`](../tests/test_retrieve.py)
> 執行評測：`uv run python -m part_assistant.eval_retrieval [--models A,B] [--show-misses]`

## 結論先講

預設流程是 **型號過濾 → 向量檢索（bge-m3）取前 20 名 → reranker 重新排序**：

```
問題 ─> 偵測型號（TEC3200？）─> 只搜尋該型號的 chunk
     ─> bge-m3 向量相似度，取前 20 名
     ─> bge-reranker-v2-m3 逐一讀 (問題, chunk)，重新排序
     ─> 前 k 名
```

這個流程是**比較 8 種組合之後，依數字選出來的**，不是照教科書挑的。教科書推薦的 hybrid（BM25 + 向量）在這份資料上**表現比單用向量差**，原因見第三節。

## 一、怎麼衡量：recall@k 和 MRR

黃金樣本中有 32 題標了答案所在的「檔案和頁碼」。對每一題做檢索，然後檢查：

- **recall@k（召回率）**：正確頁面有沒有出現在前 k 名？有一題兩個來源只找到一個時，算 0.5 分。
  - **r@5 是最重要的指標**：之後會把前 5 名交給 LLM。正確答案不在這 5 段裡，LLM 再聰明也答不出來。
- **MRR（平均倒數排名）**：正確答案排第 1 名得 1 分，第 2 名得 1/2，第 3 名得 1/3，沒找到得 0 分。它看的是「排得多前面」。
- 一個 chunk 只要來自正確的檔案，而且頁碼範圍涵蓋該頁，就算命中。

**為什麼用 recall，不用 precision（精確率）？** 檢索最怕「漏掉」，漏掉了 LLM 就無法回答。至於多找回幾段不相關的內容，LLM 會自己略過。

**樣本很小**：32 題中，一題約占 3 個百分點。相差 1 到 2 題的差距不能當真，所以**不拿這 32 題去細調參數**，以免調成只適合這 32 題的數字（過度擬合）。

## 三、為什麼 hybrid 輸了

**問題是中文，文件是英文。**

BM25 是**逐字比對**。「TEC3200 在 50% 負載時的效率是多少？」斷詞後只剩 `tec3200`、`50%`，而「效率」永遠比對不到 "Efficiency"。結果 BM25 只能分辨「哪些 chunk 提到 TEC3200」，在同一份文件裡的排名幾乎是亂的。

RRF 對兩份排名**一視同仁**，所以 BM25 的雜訊會把向量找到的正確答案往後擠。

把 BM25 的權重調低，可以挽回一部分（權重 0.1 時 r@5 = 0.92），但 r@1 和 MRR 會退步，而且差距都在 1 到 3 題之間，屬於過度擬合的範圍，所以沒有採用。

**BM25 真正的價值是精確比對料號**，例如 TEC1600 和 TEC3200 只差一個數字，向量很容易混淆。所以我們改用**型號過濾**取得這個好處：問題提到哪個型號，就只搜尋那個型號的文件。

**什麼情況下 hybrid 會贏？** 問題和文件使用相同語言時，例如 agent 改用英文關鍵字呼叫 `search_docs`。所以 BM25 和 hybrid 都保留成選項，等 agent 完成後，用端到端評測再比較一次。

**hybrid + rerank 和 向量 + rerank 的差距只有 1 到 2 題**，屬於雜訊範圍。選後者的理由是它比較簡單，而且最重要的 r@5 是 1.00。

## 四、各元件

### 1. 型號過濾（`detect_models`、`model_filter`）

- 取型號的第一段當作別名：`TEC1600-12-074xA` → `tec1600`。
- 問題的 token 裡出現某個別名，就只保留那個型號的 chunk。
- **沒有偵測到型號時不過濾**，例如「哪一台效率最高？」會在全部文件裡搜尋。
- **過濾發生在排名之前**：如果先排名再過濾，前 5 名可能被濾到只剩 1 個。

過濾使用通用的 `where=lambda chunk: ...` 參數。之後做權限過濾（`access_level`）和版本過濾（`revision`）也走同一個入口。

**做不到的事**：問題寫的是內部料號 `PSU-3200-54V` 時，問題裡沒有原廠型號，無法過濾。這要靠 agent 先呼叫 `lookup_part` 查出原廠型號（`TEC3200-54-074NA`）再搜尋，也就是黃金樣本 `multi` 類的題目。

### 2. 向量檢索（`Embedder`）

- **bge-m3**：多語模型，中文問題可以找到英文段落，最長支援 8192 tokens。
- **向量正規化成長度 1**，所以內積就等於 cosine 相似度。
- **fp16**：VRAM 用量減半、速度變快，排名結果幾乎一樣。
- **不用向量資料庫**：696 個 chunk 的向量只是一個 696 × 1024 的矩陣（約 3 MB），numpy 一次乘法就算完。等到幾十萬筆以上，才需要 HNSW 這類近似搜尋和向量資料庫。
- **快取**：`data/processed/emb/<模型名稱>.npz`，以 chunk_id（內容的雜湊值）當 key。
  - 只有新增或修改過的 chunk 需要重新 embedding（第一次 117 秒，之後 3 秒）。
  - **每個模型存成不同的檔案**：不同模型的向量座標系不同，絕對不能混用。
  - 只保存目前存在的 chunk，舊的向量會自動清除。
- **`max_seq_length = min(1024, 模型上限)`**：e5 只支援 512 tokens，輸入超過時會在 GPU 上發生 index out of bounds 而當掉（實際踩過這個坑）。

### 3. Reranker（`Reranker`）

| | embedding（bi-encoder） | reranker（cross-encoder） |
|---|---|---|
| 做法 | 問題和 chunk **各自**轉成向量，再算距離 | 把問題和 chunk **一起**讀進模型，直接打分數 |
| 準確度 | 普通：兩邊從來沒有「互相看過」 | 高：能注意到「問的是 100% 負載，這段寫的是 100% load」 |
| 速度 | 快：chunk 的向量可以事先算好 | 慢：每一對都要即時計算 |
| 用途 | 從 696 個 chunk 中**粗篩**出前 20 名 | 只對這 20 名**重新排序** |

加上 reranker 後，r@1 從 0.56 提高到 0.81，MRR 從 0.75 提高到 0.88，代價是每題多約 0.5 秒。和 LLM 生成回答需要的好幾秒相比，這是可以接受的。

**實例**：問題是「TEC3200 在 50% 負載時的效率是多少？」，答案在第 2 頁的 INPUT 表：

| 向量名次 | cosine | rerank 分數 | 新名次 | 內容 |
|---|---|---|---|---|
| 1 | 0.664 | 0.77 | 4 | p28 電源精度表 |
| 2 | 0.658 | **0.02** | 8 | p2 訂購資訊：型號拆解 `TEC \| 3200 \| 54…` |
| 3 | 0.657 | **0.98** | **1** | **p2 INPUT 表：效率和 50% load** ✓ |
| 5 | 0.641 | 0.82 | 3 | p6 均流表：`50% - 79%` |
| 7 | 0.636 | 0.85 | 2 | p3 OUTPUT：`@ 50% load` |

- **向量的分數擠在 0.636 到 0.664 之間**，幾乎分不出差別。因為每一段都是「TEC3200 的規格表」，壓縮成向量之後都很像。
- **型號拆解表被向量排在第 2 名**：它滿是 `TEC 3200`，但和效率無關。reranker 看出它答不了這個問題，給 0.02 分。
- reranker 的分數拉開到 0.02 到 0.98，正確答案拿到最高分。

**為什麼取前 20 名？** 前 10 名的 r@5 只有 0.89，前 30 名則是 0.91，反而比前 20 名差。前 30 名變差是因為候選越多，越容易混進看起來相關的干擾項；而這個差距也在雜訊範圍內。20 是常見的設定，結果也最好，所以不再細調。

### 為什麼需要 GPU（推論也需要）

我們沒有訓練任何模型，但推論同樣是大量的矩陣乘法。bge-m3 有 5.68 億個參數，每處理一個 token 大約要做 11 億次運算。同樣的工作分別在 CPU 和 GPU 上執行（筆電：16 執行緒的 CPU 對上 RTX 5070 Laptop fp16；單次量測，只看數量級）：

| 工作 | CPU | GPU | 差距 |
|---|---|---|---|
| embedding 64 個 chunk | 29.65 秒 | 0.67 秒 | 約 44 倍 |
| embedding 1 個問題 | 46 ms | 10 ms | 約 5 倍 |
| rerank 20 段（每題都要做） | 21.1 秒 | 0.56 秒 | 約 38 倍 |

| 步驟 | 什麼時候做 | 只有 CPU 時 |
|---|---|---|
| PDF 解析 | 離線做一次，結果快取 | 本來就在 CPU 上跑，約 2 分鐘 |
| embedding 全部 chunk | 離線做一次，結果快取 | 約 5 分半，可以接受 |
| embedding 問題 | 每題都要做，但問題很短 | 46 ms，CPU 就夠了 |
| **rerank** | **每題都要做**，20 段長文字 | **21 秒，無法使用** |

**真正非用 GPU 不可的只有 reranker。** 沒有 GPU 時的選擇：拿掉 reranker（r@5 回到 0.89）、換成較小的 reranker、改用雲端 API，或者讓多個服務共用一台 GPU 推論伺服器（P2）。

### 4. RRF（`rrf`）

```
score(chunk) = Σ 權重 / (60 + 在該排名中的名次)
```

只看**名次**，不看原始分數，因為 BM25 的分數（0 到 30）和 cosine 相似度（0 到 1）的尺度不同，不能直接相加。60 是原始論文建議的常數，作用是讓第 1 名和第 2 名的差距不會過大。

## 六、限制和之後的工作

1. **32 題太少**：要分辨 1 到 2 題的差距，需要更多題目。光寶內部用的是 100 題。
2. **reranker 讓每題多 0.5 秒**：可以改成只 rerank 前 10 名，或者換用更小的 reranker，取捨要用數字說話。
3. **hybrid 要再評估一次**：agent 用英文關鍵字搜尋時，BM25 可能就有用了。
4. **型號別名是規則判斷的**：問題寫成「TEC 3200」（中間多一個空格）就比對不到。
5. **只評估檢索**：檢索到正確頁面不代表回答正確，端到端評測要等 agent 完成。

## 七、可能的追問

- **「為什麼不用 hybrid？大家都說 hybrid 比較好。」**
  我們實際測過。這份資料的問題是中文、文件是英文，BM25 只比對得到型號，排名大多是雜訊，hybrid 的 r@5 從 0.89 降到 0.81。我們改用型號過濾來取得 BM25 精確比對的好處。條件改變（例如改用英文查詢）時，會再測一次。
- **「為什麼不用向量資料庫？」**
  696 個向量只占 3 MB，暴力計算不到 1 毫秒。現在加上向量資料庫只會多一個服務要維運。等規模到幾十萬筆，才需要 HNSW 這類近似搜尋。
- **「reranker 為什麼比 embedding 準？」**
  embedding 是把問題和文件各自壓縮成一個向量，壓縮時不知道對方是誰。reranker 則是同時讀兩邊，可以逐字比對條件。代價是無法事先計算，所以只用在少數候選上。
- **「怎麼避免換模型時壞掉？」**
  每個模型的向量存在不同的快取檔，而且有品質門檻測試，換模型後分數掉到門檻以下，CI 就會失敗。
