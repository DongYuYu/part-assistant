# 模型路由：地端模型只當備援

一句話：**平常全部交給 Claude；Claude 無法使用時，改用地端模型（Ollama 的 qwen3:4b），而且只給它唯讀工具。**
不依題目類型分流給地端模型，因為量測結果顯示它省不了多少錢，品質卻會下降。

程式：`src/part_assistant/local_agent.py`、`src/part_assistant/agent.py`（`FALLBACK_ERRORS`、`_fall_back`）、`src/part_assistant/circuit.py`（斷路器）。
測試：`tests/test_fallback.py`、`tests/test_circuit.py`。

## 一、量測：地端模型答得怎麼樣

同一份黃金樣本（50 題，其中 2 題是已知解析問題，不計分），同一個 system prompt、同樣的工具、同一個批改器。
地端模型跑在 **RTX 5070 Laptop（8 GB VRAM）**，Ollama 0.34.2，Q4_K_M 量化，`temperature 0`，context 16k。

| 設定 | 分數 | 總時間 | 每題平均 | 花費 |
|---|---|---|---|---|
| Claude Opus 5.5 | **48/48（100%）** | 278 秒 | 5.6 秒 | $1.38 |
| qwen3:4b（開思考） | 29/48（60%） | 1096 秒 | 22 秒 | $0 |
| qwen3:4b-instruct（不思考） | 18/48（38%） | 80 秒 | 1.6 秒 | $0 |

依類別（開思考 / 不思考），以及這類題目佔 Claude 成本的比例：

| 類別 | 開思考 | 不思考 | 佔 Claude 成本 |
|---|---|---|---|
| refuse 拒答 | 6/6 | 5/6 | 8.4% |
| tool 單純查工具 | 5/6 | 5/6 | 6.2% |
| clarify 追問 | 2/3 | 3/3 | 5.5% |
| multi 多步 | 4/4 | 1/4 | 10.0% |
| spec 規格 | 5/12 | 1/12 | 24.6% |
| table 表格 | 4/6 | 2/6 | 20.1% |
| similar 相似型號 | 2/4 | 0/4 | 13.0% |
| footnote 註腳 | 1/4 | 0/4 | 7.9% |
| ticket 工單 | 0/3 | 1/3 | 4.3% |

看分數不如看錯在哪裡：

1. **不思考就不查資料**：不思考的版本有 17 題完全沒呼叫工具，例如把廠商型號 CSU2400AT 當成內部料號，直接回「查無資料」。開思考後只剩 5 題。
2. **照抄 prompt 的範本**：7 題把引用寫成 `(file p.N)`，沒有填入真正的檔名。
3. **推理過程漏進回答**：`qwen3:4b` 這個標籤指向只會思考的版本，`think: false` 關不掉。Ollama 的模板吃掉了開頭的 `<think>`，只剩結尾的 `</think>`，整段英文推理都變成了回答內容。
4. **謊稱做了某件事（最危險）**：開思考的版本有一題回答「已開立高嚴重度工單」，但它根本沒有呼叫 `create_ticket`。資料庫沒有被寫入（只有工具能寫），但使用者會被誤導。

第 2、3 點原本的關鍵字批改**抓不到**，因為回答裡有正確的數字。所以批改器加了 `check_format`：出現 `<think>` 標籤，或照抄 `(file p.N)` 範本，一律判為失敗。

## 二、為什麼不依題目類型分流

地端模型答得好的類型（拒答、單純查工具、追問）合計**只佔 Claude 成本的 20%**。這些題目不必翻 datasheet，token 少，在 Claude 上本來就便宜。
錢花在要查大型表格的題目（規格、表格、相似型號），而這些剛好是地端模型答錯的。

所以就算分類器完全不出錯，最多也只省 20%；代價是那幾類的品質從 100% 掉到 67%–100%，而且每題都要多花分類的時間。**在這份題目組成下不划算。**

這個結論依賴題目組成。如果實際流量裡大部分是「某料號還有多少庫存」這種題目，結論就會不同，到時候應該用實際流量重新量測。

真正能省錢的地方是**減少檢索結果的 token**（例如 FRU 大表格的雜訊，見 README 已知限制）和 prompt caching（已經在用）。

## 三、降級怎麼運作

```
問題 → 斷路器打開了嗎？
        ├─ 是 → 直接用地端模型（不碰 Claude）
        └─ 否 → Claude
                 ├─ 成功 → 正常回答，失敗次數歸零
                 └─ 失敗（SDK 已自動重試 2 次）
                       ├─ 連不上、逾時、5xx（含 529 過載）、429 → 失敗次數加一，改用地端模型，從頭回答這一題
                       └─ 400、401、403 → 直接丟出錯誤，不降級，也不算進失敗次數
```

- **只有「Claude 暫時無法使用」才降級**。400（請求格式錯）、401（key 錯或過期）是我們自己的問題，降級會把它藏起來，key 過期了也不會有人發現。
- **地端模型只拿到 3 個唯讀工具**：`search_docs`、`lookup_part`、`check_stock`。`create_ticket` 根本不傳給它；就算它還是呼叫了，`LocalAgent._run_tool` 也會拒絕。兩道防線，都寫在程式裡，都有測試。
- **system prompt 多一條規則**：現在不能開工單，請使用者稍後再試。這是為了避免上面第 4 點「謊稱開了單」。
- **每個降級回答開頭都有警告**：「⚠ 降級模式：雲端模型暫時無法使用，以下由地端模型回答，請自行核對來源。」
- **Claude 在失敗前做過的事會保留**：如果 Claude 在第 2 步才失敗，第 1 步的工具呼叫、成本和 trace 都會留在結果裡；高嚴重度工單的草稿也會保留，仍然要人工確認。
- **Ollama 也掛了**：回答「雲端和地端模型都暫時無法使用，請稍後再試」，`stop` 是 `unavailable`，程式不會當掉。
- **trace 會記錄降級**：多一筆 `{"type": "fallback", "reason": "APIConnectionError: ...", "to": "qwen3:4b"}`，trace 檔也有 `degraded: true`。
- **斷路器**：連續 3 次失敗後打開，接下來 60 秒的題目直接走地端模型，不再等 Claude 重試。60 秒後放一題去試 Claude（half-open）：成功就關上，失敗就再開 60 秒。詳見下一小節。
- **評測不用降級**：評測要量的是 Claude 的分數，混入地端模型的回答，分數就沒有意義了。`build_eval_agent` 不傳 `fallback`。

實測（同一台電腦，把 SDK 指向一個沒有服務的 port，模擬 Claude 連不上；請求沒有送到 Anthropic，不花錢）：

| 問題 | 結果 |
|---|---|
| PSU-3200-54V 還有多少庫存？ | 降級回答「總計 296」，和資料庫的 `total_available` 一致；地端兩次呼叫共約 25 秒 |
| PSU-3200-54V 冒煙，請開一張高嚴重度工單 | 降級回答「無法立即開立高嚴重度工單，請稍後再試」；工單數量不變 |

### 斷路器（circuit breaker）

沒有斷路器時，Claude 故障期間的**每一題**都要先等 SDK 重試失敗，才會降級。要等多久，看是哪一種故障：

| 故障 | SDK 放棄前要等多久（實測／預設值） | 斷路器每題省多少 |
|---|---|---|
| 連不上（port 沒開、DNS 錯） | 實測約 1.4 秒（3 次，含重試間隔） | 約 1.4 秒，很少 |
| 逾時（收了請求卻不回應） | 預設 read timeout 600 秒 × 3 次，最壞約 30 分鐘 | 幾乎全部 |
| 5xx、429 | 伺服器會很快回錯誤，通常幾秒 | 幾秒 |

所以斷路器主要是為了**逾時**這種最糟的情況：前 3 題還是要等，之後的題目就不用等。

- **狀態存在檔案裡**（`data/processed/circuit.json`）：CLI 每問一題就是一個新的程序，狀態放在記憶體裡會跟著程序消失，斷路器永遠打不開。Docker 裡這個檔案在 `processed` volume，容器重建也會保留。
- **檔案壞掉或不見就當作關閉**：斷路器出問題時，最多是「沒有保護」，不會「誤擋 Claude」。
- **寫檔是原子操作**：先寫暫存檔再 `replace`，讀的人不會看到寫一半的檔案。
- **401、400 不算失敗**：那是設定錯誤，不該讓斷路器打開；而且它們本來就不降級，會直接報錯。
- **trace 會記錄原因**：斷路器打開時，fallback 事件的 reason 是 `circuit open (23s left)`，看得出是斷路器擋下的，不是 Claude 當下失敗。

實測（同一台電腦，`ANTHROPIC_BASE_URL` 指向沒有服務的 port，不花錢），連續問 4 題「PSU-3200-54V 還有多少庫存？」：

| 題 | 降級原因（trace） | 斷路器狀態（之後） |
|---|---|---|
| 1 | `APIConnectionError` | 失敗 1 次 |
| 2 | `APIConnectionError` | 失敗 2 次 |
| 3 | `APIConnectionError` | 失敗 3 次 → 打開 |
| 4 | `circuit open (23s left)`，沒有連 Claude | 仍然打開 |

4 題都回答 296，和資料庫一致。每題總時間 36–53 秒，大部分是地端模型（RTX 5070 Laptop）；連不上的情況斷路器只省約 1.4 秒，被地端模型的時間差蓋過去了，所以總時間看不出差別。

設定（環境變數）：`PART_ASSISTANT_LOCAL_MODEL`（預設 `qwen3:4b`）、`OLLAMA_HOST`（預設 `127.0.0.1:11434`，和 ollama 指令用的是同一個變數）。

## 四、限制

- **地端模型慢**：開思考每題約 20–30 秒，Claude 約 5 秒。降級時使用者要等比較久。
- **品質只有 60%**：所以回答都有警告，請使用者自行核對來源。
- **會洩漏 prompt 的內容**：實測時有一次回答結尾多了「(規則 8)」，把 system prompt 的規則編號露給使用者。不影響安全，但不好看。
- **斷路器的門檻是寫死的**：3 次、60 秒，沒有依實際故障情況調過。
- **多個程序同時寫狀態檔時，計數可能少算**：兩個程序同時讀到「失敗 2 次」，都寫回 3，實際是 4 次。後果只是斷路器晚一題打開，所以不加鎖。真的多人同時使用時，狀態應該放到 Redis 這類共用的地方。
- **逾時還是要等 600 秒**：斷路器只保護「之後」的題目。把 timeout 調短可以讓前 3 題也快一點，但 Claude 寫長回答本來就要一段時間，調太短會誤判，要先量 p99 的回應時間再決定，目前沒有調。
- **MCP server 沒有降級**：用 MCP 時，模型是 host（例如 Claude Code）在跑，不是我們。

## 五、常見問題（Q&A）

### Q：為什麼地端模型不拿來分擔平常的流量，省成本？
量過了。地端模型答得好的題型只佔成本的 20%，而且那幾類的品質也會下降。錢花在要查大表格的題目上，那剛好是 4B 模型做不好的。見第二節的數字。

### Q：為什麼 401 不降級？
401 代表 key 錯或過期，是設定問題，不是 Claude 暫時無法使用。降級會讓系統看起來還在運作，但品質掉到 60%，而且沒有人會發現 key 該換了。錯誤要大聲報出來。

### Q：只在 prompt 裡寫「不要開工單」不夠嗎？
不夠。量測時地端模型就曾經「說」自己開了單。所以工具清單裡根本沒有 `create_ticket`，執行時也會拒絕；prompt 那條規則只是讓它的回答比較誠實。

### Q：為什麼降級是整題重來，不是從 Claude 失敗的那一步接著做？
兩個模型的訊息格式不同（Anthropic 的 content blocks 和 Ollama 的 messages），Claude 的 thinking 區塊地端模型也看不懂。整題重來比較單純，代價是可能重複查一次工具；工具都是唯讀的，重複查沒有副作用。

### Q：為什麼用 qwen3:4b 開思考，不用更快的 instruct 版？
instruct 版每題 1.6 秒，但只有 38%，而且有 17 題沒查資料就回答。降級時寧可慢，也不要不查就答。

### Q：斷路器為什麼不直接放在記憶體裡？
這個專案的 CLI 每問一題就是一個新的程序，記憶體裡的計數每次都從 0 開始，斷路器永遠打不開。所以存成檔案。如果改成一直開著的服務（例如 HTTP API），放記憶體就夠了；多台機器時則要放 Redis 這類共用的地方。

### Q：斷路器打開時，為什麼不直接回「服務暫停」，而是用地端模型？
地端模型能答 60% 的題目，而且回答都有警告。直接拒答的話，連「還有多少庫存」這種地端模型做得到的題目都答不了。

### Q：為什麼要有 half-open？
不然斷路器打開後不知道什麼時候該關。60 秒後只放一題去試：Claude 恢復了就關上，沒恢復也只多等一題。

### Q：測降級要不要花錢？
不用。單元測試用會丟錯誤的假 client；實測則把 `ANTHROPIC_BASE_URL` 指向本機一個沒有服務的 port，請求不會送到 Anthropic。
